C16QS Documentation Intelligence: Architecture and Validation Note

Cavli Round 3, Assignment 2 · Nishan · 15 November 2026 · Python CLI + hosted web prototype · Public sources only

1. What was built

A repeatable pipeline ingests four public sources for the Cavli C16QS LTE Cat 1bis module:

  • Hardware Manual 5.3
  • EVK User Manual 1.1
  • AT Command Manual 3.1
  • The official product page

The pipeline indexes 659 passages with page, section and revision metadata. Answers are cited to document, revision and printed page or web section. The system also:

  • flags ambiguity (bare module vs EVK; regional variant)
  • refuses unsupported inferences
  • sends conflicts, broken cross-references and revision changes to an expert review queue.

2. Architecture

The local CLI (python -m docintel ingest | ask | sources | review | simulate-revision | eval | publish) and the website show the same fields for every answer:

  • the status: answered, answered with flags, ambiguous, conflict or not verified
  • the answer, plus a clarifying question when the question is ambiguous
  • citations: title, revision and its status, printed page (and PDF page), section, a deep link (#page=N or #anchor) and the quote
  • review flags, the retrieved passages with their scores, the mode used, and the elapsed time.

Hosted prototype

Live site: cavli-assignment-2.nishanameenk.workers.dev, behind a reviewer login. It's a Cloudflare Worker serving four tabs (Ask, Review queue, Pipeline and Sources) plus a switch to the simulated-revision view.

  • Engine. web/src/engine.ts is a line-for-line TypeScript port of the answer engine, so the hosted and local runs are scored by the same code.
  • Data. It lives in a separate docintel schema in the existing Supabase project. The schema isn't exposed through the API, has RLS enabled and no policies, and only the service role can call its SQL functions. A token-checked edge function sits in front.
  • Tokens. The runtime token is read-only. The publish token can write and expires. Only SHA-256 hashes are stored.
  • Search. Postgres full-text search (ts_rank) replaces SQLite BM25 for candidates. The rerank after it is the same. Every passage also has a gte-small and a Gemini vector, so hybrid search can be selected per request (§4).
  • Pipeline tab (read-only). It shows the five stages with real counts, a per-document table, the revision timeline and run history. Its "Check sources for updates" button compares live ETag and size (PDFs) or visible text (product page) with the fingerprint recorded at publish time. It only detects change: re-indexing stays in the controlled pipeline because it needs human approval.
  • Publishing. python -m docintel publish pushes the verified index (current and simulated views). It's idempotent, and an expert's resolutions survive re-publishing.

Assignment 1's Worker, tables and function are untouched.

3. Ingestion and source updates

  • Identity vs revision. documents holds stable identity: title, publisher, type and scope. revisions holds the following per revision: label, date and where the date came from, URL, host, file SHA-256, extracted-text SHA-256, acquisition route, status, the simulated flag and the page-label offset. Page numbers are never invented. Each page's printed label is kept only when it matches the offset found across the document (EVK: printed = PDF + 1). Web passages carry section names and anchors, not pages.
  • Repeatable and idempotent. Re-running ingest leaves an unchanged text hash marked unchanged. That was verified twice, and with a live product-page refresh whose raw HTML had changed but whose text hadn't. A from-scratch run with an empty cache rebuilt the same 659 passages in 13 s.
  • Revisions. A new revision row is ingested next to the old one. The newest becomes current and the older one becomes superseded but stays retained. The pipeline then diffs the pages, records the changed lines with old and new passage IDs, and adds a revision_change review item (severity high if any number changed).
    • Normal retrieval reads current revisions only. --all-revisions shows both, labelled OUTDATED.
    • A PDF whose bytes change at the same URL stops ingest, so a person must add a manifest entry.
    • A product page whose text changes becomes a new dated snapshot.
  • Demonstration (simulated, labelled). The v5.1 manual couldn't be retrieved: one host timed out and the mirror sits behind a browser check. So 5.4-SIMULATED applies two edits to the stored 5.3 text, changing the reset pulse to 150–500 ms. Re-indexing superseded 5.3 and isolated the changed sentence on p. 31. The answer now cites 5.4 with a SIMULATED warning, shows the previous 5.3 wording, and links review item #7. Re-applying it gives unchanged. The simulation never touches the main index.

4. Retrieval and answer generation

Keyword retrieval (the local CLI, and one half of the live hybrid search): SQLite FTS5 with BM25 (Postgres full text on the live site) (section text weighted ×2), then a transparent rerank. The rerank combines normalised BM25, the share of question keywords covered (with domain expansions such as reset → RSTN and units such as "5V" → voltage), and a bonus for exact phrases (JMP 3, AT$QCRST, pin numbers). It also applies scope rules: EVK vs module hints, a penalty for the AT manual on non-command questions, and a penalty for unsectioned front matter. Results are de-duplicated per page.

Measured in three steps. The 24 evaluation questions use the manuals' words, so three everyday-wording sets were written, each before the change it tested: A (14), B (12) and C (10 answerable plus 6 that must be refused, with the decision rule written into the file). Hybrid search fuses keyword and pgvector results (reciprocal rank fusion). The gate decides whether the model is asked: a word-overlap pre-filter, or the model itself judging the passages.

Answering follows a fixed order of checks.

  • Guardrails. Battery life without a duty cycle, and certification of a custom antenna or product, return "Not verified in the available C16QS sources". The related passages are shown as context only, with an escalation route.
  • Band questions are answered from structured per-variant band claims, never by the model. No variant → ambiguous, with a clarifying question. A disputed band → conflict: both passages are shown, nothing is confirmed, and the review item is linked.
  • Supply-voltage questions without a scope → separate module and EVK answers plus a clarifying question.
  • Otherwise → gemini-3.1-flash-lite (temperature 0, JSON output) sees only the retrieved passages. It must cite passage IDs in every sentence and may return not_verified.

5. Accuracy controls and validation

  • Answer validator. Every cited ID must be among the retrieved passages, and every number in the answer must occur as a whole number in a cited passage. Otherwise the answer is rejected and replaced by an extractive quote, and the reason is recorded. In a unit test the validator accepted "100-500ms" and rejected an invented "150".
  • Answerability. On the live site the model judges whether the retrieved passages answer the question, and may return "not verified". If the model is unavailable, the answer is "not verified", never quotes posing as an answer. The local CLI keeps a word-overlap pre-filter (40% of keywords) before the model.
  • Citation verification in evaluation. Each cited page is re-extracted from the hash-verified source file. The quote must appear on that page with the same printed label. Every citation in every scored run passed (125/125 across the final live runs).
  • Review flags attach by topic and cited passage (for example, the AT+TRB gap appears on answers that cite p. 31). Answers that rely on conflicting, changed or undocumented evidence get the status "answered with flags"; the low-severity outdated-reference flag is shown without changing the status.

6. Security and privacy

  • Hosted access. Every page and API call needs the reviewer login; anonymous requests get 401. Secrets are Worker secrets only. The CSP is strict (script-src 'self'), and the page inserts server text with textContent, never as HTML.
  • Keys. The Gemini key lives only in the git-ignored .env. It's read from the environment, sent only as the x-goog-api-key header, and never logged, stored or packaged. .env.example holds the variable names only.
  • Data. Only public documents and the user's question go to the model. No customer data, internal Cavli systems or credentials are used.
  • Untrusted input. Downloaded files are treated as data. PDFs are parsed, never executed. Pinned hashes catch tampering or silent replacement. Browser checks are never bypassed.
  • Human approval. Conflicts and revision changes are never auto-resolved. An expert resolves them with review --resolve ID --note. Nothing is published or sent to customers.

7. Models, services, costs and limits

  • Software. Python 3.12 standard library, plus pypdfium2 5.13 and SQLite FTS5 for the CLI. Hosted: a Cloudflare Worker, plus Supabase Postgres with pgvector and an edge function (gte-small built in). No paid service.
  • Quotas. gemini-embedding-001 allows 1,000 requests/day per Google project on the free tier. Documents are embedded once through a content-addressed cache; each hybrid question needs one call. A backup key from a second project takes over after a 429, for embeddings and answers. If both fail, the site falls back to keyword search and says so.
  • Model. Google Gemini gemini-3.1-flash-lite through the Generative Language API, using the key already created for Assignment 1 (a separate local copy; Assignment 1 is untouched). A generated answer averaged about 1,650 input and about 100 output tokens. Median latency was about 1.4 s. A retried call took 8–15 s, and calls are capped at 20 s plus one retry. Retrieval runs locally in about 5–50 ms. Cost per answer is small, but rate limits and pricing depend on the key's Google tier, which I haven't confirmed. Without a key everything still works in extractive mode (11/14).

8. Assumptions, simulations and known limitations

  • Simulated: hardware manual revision 5.4 (labelled everywhere). Not implemented: scheduled re-ingest, a repair retry for rejected citations, and an entailment check at the level of individual claims.
  • Answers that sit in long mixed tables are still hard to retrieve ("thickness", "how big", "peak transmit current"). The next lever is row-level table passages. The answerability decision relies on the model's judgement, with guardrails and the validator around it.
  • The three manuals come from distributor or vendor hosts. Identity is confirmed from Cavli's cover pages and version history, but there's no official download URL.
  • Scope, variant, guardrail and band parsing are rule-based for this module family. Other products would need new patterns.
  • Table cells can extract out of order, so a section label near a table can be off by one, though the page stays correct. Figures and images aren't read.
  • The validator checks citations and numbers, not every claim. The held-out H07 answer turned the eSIM legend into an "H suffix" rule without the validator noticing.
  • An evaluation of 24 questions is a smoke test, not a benchmark.
